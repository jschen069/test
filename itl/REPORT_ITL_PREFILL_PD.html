00结论先行

如果只看 mean、TPOT 或 P99，这三次运行都很稳；尖刺全部藏在最大值里，而且有明确的 step 级成因。

  1. 均值与 TPOT 是健康的，问题只在尾部。vLLM bench 的 Max ÷ Mean 在 4×4 是 9.9×、64×16 复测是 9.0×，aisbench 是 9.7×；aisbench 99% 的 ITL 都在 44.3ms 以下。
  2. 尖刺与一批新请求的 prefill 进入同一个 engine step 精确对齐。vLLM 4×4 的 0.691s / 1.030s 两个 step 边界、vLLM 64×16 与 aisbench 的各自四次波次，长间隔的结束时刻都与同一 step 释放的整批 token 重合（差 ≤0.2ms）。
  3. 两套 benchmark 都不测 GPU step，而是测客户端 SSE chunk 的到达间隔。vLLM bench 只对 choices chunk 计时，1024 token → 1023 个 ITL；aisbench 对每个非空 data: 行计时（含最后的 usage chunk），1024 token → 1024 个 ITL。两者默认都不打印 max。
  4. PD 能移走 339–397ms 这一档，但移不走 D 自身的 50–98ms 同步停顿。KV 传输在长上下文 + 慢链路下会制造新的、甚至更大的尖刺：32K token 在 3GB/s 下约 716ms。
证据边界：本文所有判断基于客户端时间戳对齐，不是服务端 GPU step trace。ITL 里包含服务端调度、排队、HTTP/SSE、客户端事件循环等全部环节；后文的“同一步”是由多个请求的 token 在同一毫秒级窗口到达推断出来的，不是直接读调度器日志。

01Prefill 为什么会挤占 Decode

vLLM v1 的一个 engine step 同时装两类工作：running 请求的 decode，以及新请求（或未完成请求）的 prefill chunk。一个 step 的所有输出在 step 结束时一起返回。于是“某个请求的 ITL”不只是它自己的 decode 时间，而是它所在 step 的墙钟时长。

电梯类比：decode 像电梯每层都停；prefill 像有人搬大件上电梯。搬大件的那一趟，整趟时间变长，电梯里所有人都晚到。你不会说“电梯每层变慢了”，因为下一趟立刻恢复正常——这正是数据里 340ms 与 34ms 交替出现的原因。

1.1 微观证据：0.691s 与 1.030s 的两个 step

4 个请求在 4ms 内先后发出，输入长度 49–75 token。前三个 step 分别耗时 353ms、338ms、339ms；四个请求都进入 decode 后，step 立刻降到 34–40ms。关键是谁和谁一起到达：

  • 0.353s：只有 req0 的首 token。
  • 0.689–0.691s：req0 的第 2 个 token，与 req1、req2 的首 token 同时到达。
  • 1.027–1.030s：req0/1/2 的第 2 个 token，与 req3 的首 token 同时到达。

req0 的前两个 ITL 分别是 338.5ms 和 339.3ms，正好等于这两个 step 的墙钟。若这是网络抖动，不可能四个请求在同一个 step 边界一起恢复；若这是 decode 变慢，后面不会立刻回到 34ms。

1.2 为什么 mean 和 TPOT 看不出来

TPOT 把整段生成摊平：

TPOT = (latency − TTFT) / (N − 1)    mean ITL = sum(ITL) / (N − 1)

一次 339ms 的 step 落在 1023 个 token 上，只给 TPOT 增加约 0.33ms；而它单独出现时，就是一个 339ms 的 ITL。vLLM bench 的 mean ITL 与 mean TPOT 因此完全相同（1023/1023 = 1.0000）。aisbench 因为多记了最后的 usage chunk，比值是 1023/1024 = 0.9990，但差异只有 0.1%，同样掩盖不了尾部。

结论：“ITL 比 TPOT 大很多”不是平均意义上的大，而是最大值与分布尾部的大。任何只报告 mean / TPOT 的压测，都会把这类问题判为“正常”。

1.3 aisbench：同一机制在 64 并发下放大

aisbench 的 64 个请求分 4 波、每波 16 个，波次起点在 0 / 42.5 / 85.4 / 127.5s。每波的第一个请求都会出现一次 384–397ms 的长间隔，而长间隔的结束时刻与同波其余 15 个请求的首 token 时刻几乎完全重合：

恒等式： sum(ITL) = latency − TTFT；len(ITL) = n_chunks − 1； mean(ITL) / TPOT = (n_tokens − 1) / (n_chunks − 1)。 vLLM bench 的 n_chunks = n_tokens，所以严格相等；aisbench 多一个 usage chunk，所以是 1023/1024。 如果某个服务把多个 token 打包进一个 chunk，mean ITL 会按每 chunk 的 token 数成倍放大，这是另一个独立问题（例如 Kimi-K3 dspark 上观察到的 2×）。

直接验证：1.5 的同形状对照中，vLLM bench 64×16 与 aisbench 64×16 的 Mean ITL 分别是 40.75 / 40.79ms，Max 是 366.1 / 397.1ms，≥100ms 的间隔都只有 4 个。计时点差异（是否记录 usage chunk）只影响 0.1% 的均值，远小于一次 prefill step 造成的尾部。

2.4 Max 到底从哪里来

两套工具的 max 都只是样本最大值，没有模型、没有外推：

  • vLLM bench：默认 --metric-percentiles 99，只打印 P99；加 99,100 后打印 P100 ITL (ms)，其值等于 np.percentile(itls, 100)，也就是 max。CLI 不会校验 100 这个输入。
  • aisbench：stock summary 不打印 max；_write_itl_tpot_diag 在 diag JSONL 里写 itl_stats_s.max_s，同时保留完整 time_points_abs_s，可以复核每一个间隔。
# vLLM bench：让 CLI 打印 P100 vllm bench serve ... --metric-percentiles 99,100 ... P99 ITL (ms): 39.36 P100 ITL (ms): 339.26 # aisbench：diag 记录里的 max_s "itl_stats_s": {"count": 1024, "sum_s": 42.17, "mean_s": 0.04118, "min_s": 0.0000346, "max_s": 0.3839, ...}

不要用 mean + 3σ 去推 max：这类尾部不是正态分布，而是由“长 step”这种离散事件主导的，σ 会被 99% 的正常样本压得很小。

03PD 分离能治多少，KV 传输会不会制造新的尖刺

PD 把 prefill 从 decode 实例的时间线里拿走，能消掉“新请求 prefill 拉长 step”这一档尖刺；但它把成本换成了 KV 传输。传输是否影响 ITL，取决于它是否在 D 的关键 step 上、以及链路是否被占满。

3.1 能消掉哪一档

把两份数据里的长间隔按来源拆开，PD 的收益和边界就很清楚：

收益上限：在这三份数据里，去掉 prefill 类尖刺后，剩下的最大间隔是 vLLM 4×4 的 53.2ms、vLLM 64×16 的 98.1ms、aisbench 的 94.8ms。 也就是 max 从约 339–397ms 降到约 98ms 以内（3.5–4×），不是降到 0。 前提是 P 与 D 真正资源隔离；若共享 GPU/网卡，prefill 仍会拖慢 decode。

3.2 KV 传输的成本

Qwen3.6 的 KV 只算全注意力层：2（K+V）× 16 层 × 4 个 KV head × 256 head_dim × 2 字节 = 65,536 B/token = 64 KiB/token。短 prompt 的 KV 很小；长上下文则完全不同。

3.3 传输在什么条件下会变成 ITL 尖刺

PD 之后，一次请求的 KV 传输位于它自己的首 token 关键路径上，正常只增加 TTFT，不影响其他运行中请求的 ITL。下面五种情况会把传输推到 decode 的关键路径上，产生与 prefill 同构的长 step：

  1. D 同步等待 KV load。调度器在某个 step 里等传输完成才开始 forward，这个 step 的墙钟就是传输时间；该 step 内所有 decode 的 ITL 一起被拉长。
  2. 传输与 decode 共享带宽。PCIe / NIC / HBM 被 KV 拷贝占满，decode step 的访存变慢；同机 PD 尤其明显。
  3. 多请求并发传输。波次式到达（就像 aisbench 每 42.5s 来 16 个请求）会让 16 份 KV 同时排队；队首阻塞把最坏传输时间放大到“单份时间 × 队列深度”。
  4. P/D 不均衡。P 产 KV 的速度长期高于 D 消费的速度，D 侧的 KV 队列变长，传输等待不可预测；反之 D 空闲则主要浪费吞吐，不会产生大 ITL。
  5. 共享资源 / 混合模型。P 与 D 同卡时，prefill 计算仍抢 D 的 SM；Qwen3.6 还有 48 层线性注意力，除 KV 外还要传 recurrent state，量小但协议必须支持，否则会走慢路径。
判断方法：先看 D 的 step duration 是否在 KV load 时出现长尾，再看传输队列深度与 NIC 利用率。若把传输改成独立链路 + 异步流水后长尾消失，说明问题在传输；若长尾仍在，说明是 D 自身的调度/客户端停顿，PD 不背这个锅。

04结论与建议

  1. 先把“大”定义清楚。如果 SLA 看 mean / TPOT，这三次运行没有问题；如果 SLA 看 max / P99.9，就必须把尾部单独监控。建议报告里同时给出 Mean、P99、P99.9、Max，并注明每个值的来源。
  2. 压测要制造“同时到达”。vLLM bench 64×16 与 aisbench 各自四次波次尖刺说明：同步到达会把 prefill 集中到一个 step，暴露最坏情况。用固定 request rate 的平滑流量，可能永远看不到 366ms / 397ms。必要时用 --burstiness 或客户端 jitter 做两组对照。
  3. 先限制单 step 的 prefill 预算，再考虑 PD。降低 max_num_batched_tokens / chunk 大小可以把长 step 切短，代价是吞吐；这是不改架构就能验证的对照组。若切短后 max 明显下降，说明确实是 prefill 挤占。
  4. PD 的验收标准要包含残余停顿。在本数据里，PD 的预期上限是 max ≈ 95–98ms，而不是 0；如果 SLA 要求 <50ms，还要继续查 D 的同步停顿（调度、CUDA graph、客户端事件循环）。
  5. KV 传输按“每请求字节 × 并发 ÷ 有效带宽”做预算。65-token 的 4 MiB 可以忽略；8K 的 512 MiB 在 3GB/s 下是 179ms，已经不可忽略；32K 的 2 GiB 是 716ms。把传输放在独立 RDMA 链路、异步流水、分块传输，并给 D 侧 KV 队列设上限。
一句话：ITL 的尖刺不是“decode 变慢”，而是“decode 和别人共享了一个长 step”。PD 把 prefill 移走，但只有当 KV 传输不在 D 的关键 step 上时，才真正把长 step 移走；否则只是把 339ms 的 prefill 尖刺换成了 716ms 的传输尖刺。

可操作的检查清单

问题看什么判据
尖刺是不是 prefill 引起的？长 ITL 的结束时刻是否与一批请求的首 token 重合重合（±几 ms）→ prefill step；不重合 → 继续查
是不是客户端停顿？同一时刻所有请求是否一起停；客户端 CPU / GC / 事件循环全部同步且服务端无异常 → 客户端或共享 step
PD 后传输是否成为新瓶颈？D 的 step duration 与 KV load 时间是否重叠；NIC 利用率重叠且长尾随传输量变化 → 传输在关键路径
长上下文是否安全？tokens × 64KiB ÷ 有效带宽> 目标 step 上限 → 需要更高带宽或分块

A.1 数据来源

  • vLLM bench（4×4）：4 个请求 × 1024 output token，max concurrency 4，输入长度 49–75 token；运行时长 35.81s；耗时数据取 --save-detailed 的 per-request itls / ttfts / start_times。
  • vLLM bench（64×16）：2026-11-01 补测，64 个 prompt × 1024 output token，max concurrency 16，request-rate inf，使用 gsm8k 定制数据集（共 4,522 input token）；运行时长 169.48s；同样取 --save-detailed 的逐请求数据。
  • aisbench：64 个请求 × 1024 output token，分 4 波、每波 16 个；输入长度 26–127 token；diag JSONL 含 time_points_abs_s，本文从原始时间点重新计算 ITL，而不是只读汇总。

A.2 复现 vLLM 的 max

vllm bench serve ... \ --num-prompts 4 --max-concurrency 4 \ --random-input-len 65 --random-output-len 1024 \ --percentile-metrics ttft,tpot,itl \ --metric-percentiles 99,100 \ --save-detailed --save-result

关键是 --metric-percentiles 99,100（让 CLI 打印 P100=max）和 --save-detailed（保留逐请求 itls）。

同形状的 64×16 复现（即 1.5 的数据）：

vllm bench serve \ --host 127.0.0.1 --port 8005 --model qwen3.6 \ --tokenizer /home/weights/Qwen3.6-27B \ --dataset-name custom --dataset-path /workspace/itl_diag/gsm8k_prompts_custom.jsonl \ --num-prompts 64 --max-concurrency 16 --request-rate inf \ --ignore-eos --custom-output-len 1024 \ --save-result --save-detailed \ --result-dir /workspace/itl_diag/vllmbench_run \ --result-filename mytest_qwen36_4x111.json

CLI 仍只打印到 P99；加 --metric-percentiles 99,100 会多一行 P100 ITL，也可以从 detailed JSON 的 itls 重算（本文即如此）。

A.3 复现 aisbench 的 max

aisbench 的 stock summary 不打印 max，但 diag 文件里有：

jq -r '.itl_stats_s.max_s' itl_tpot_diag/*.db.jsonl | sort -n | tail -1 # 或用 time_points_abs_s 自己算： python3 - <<'PY' import json mx = 0 for line in open("itl_tpot_diag.db.jsonl"): tp = json.loads(line)["time_points_abs_s"] mx = max(mx, max(b - a for a, b in zip(tp[1:], tp[2:]))) print(mx) PY

A.4 口径与局限

  • 客户端观测：ITL 包含服务端 step、排队、HTTP/SSE、客户端事件循环；不是 GPU kernel 时间。文中的“同一步”由多个请求的 token 在同一毫秒级窗口到达推断，未读取调度器 trace。
  • 单次运行：每份数据各一次；最大值的具体毫秒数会有运行间波动，但“均值≈TPOT、max 远大于均值、尖刺与首 token 对齐”的结构在三份独立运行（vLLM 4×4、vLLM 64×16、aisbench 64×16）中都出现。
  • 负载可比性：vLLM 4×4 与 64×16 的绝对均值不可直接比较（34.30 vs 40.75ms，每个 step 的并发不同）；真正的同形状对照是 vLLM 64×16 vs aisbench 64×16（40.75 vs 40.79ms）。
  • 输入分布差异：vLLM 64×16 使用 gsm8k 定制集（64 条共 4,522 input token，平均约 71 token），aisbench 为 26–127 token；输入越长 prefill step 越重，因此 aisbench 的 384–397ms 略大于 vLLM 的 338–366ms，方向一致。
  • PD 数值是预算，不是实测：3.1 的“PD 后预期”由“去掉 prefill 类尖刺后的残余最大间隔”推得；3.2 的传输时间是 bytes / bandwidth 的下界，不含排队与协议开销。
