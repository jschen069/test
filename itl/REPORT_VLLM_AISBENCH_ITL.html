ITL 计算口径 · 实测分析

同一条 SSE，两种 ITL 口径

vLLM benchmark 用相邻 choices 块做差；aisbench 用 diff(tp[1:])， 把最后的 usage 行也算进去。先用 64 条 × 1024 token 的抓包拆开“只差 1 个间隔”， 再用 32 条 × stream_interval=4 的抓包看 ITL 如何从逐 token 变成每 4 token。

Qwen3.6-27B · TP=4 64 prompts · 16 并发 1024 output tokens · ignore_eos=true stream_interval=1 追加：Qwen3-8B · NPU 6/7 · TP=2 · 32 prompts · 8 并发 · stream_interval=4

结论先行

差异不在尖峰，而在最后一个间隔

两条请求都生成 1024 个 token。vLLM 的第一个 choices 块只算 TTFT， 后续 1023 个块产生 1023 个 ITL；aisbench 把最后的 usage 也当作一个 data 行，因此产生 1024 个 ITL。

实测中，多出来的 usage 尾间隔只有亚毫秒级，所以两种规则在 64/64 条请求上 得到相同的 max。真正的大尖峰发生在 choices 之间，是 prefill / 调度阻塞， 不是 usage 计入造成的。

01 · 计数口径

同一串 SSE，谁被打了时间点

每个 SSE 事件是一行 data: 加一个空行。vLLM 只给 choices 非空的块打时间点；aisbench 在解析 JSON 前，给每个非空 JSON data 行打时间点 （usage 也算；[DONE] 不计）。

代理逐物理行记录，所以同一请求里 choices 落在 seq 0、2、4……， 空行落在 1、3、5……；seq 是行号，不是 token 序号。

测量路径 benchmark client → sse_log_proxy :8005 → vLLM :8015 代理外挂在两者之间，不属于任何 benchmark；tr=代理读到该行，tf=代理转发完该行，dt=tr − 上一条物理行 tr，都不是 benchmark 客户端的接收时间。

vLLM benchmark

第一个 choices 只算 TTFT，后续 choices 才产生 ITL

choices 规则
choices 1 → choices 2 → choices 3 ··· choices 1024 usage [DONE]
itl = diff(t₁ … t₁₀₂₄)
count = 1024 − 1 = 1023

aisbench

第一个 data 行是 TTFT 的终点；usage 也进入 ITL

data 规则
choices 1 → choices 2 → choices 3 ··· choices 1024 usage [DONE]
itl = diff(tp₁ … tp₁₀₂₅)
count = 1025 − 1 = 1024

字段与算式对照

量vLLM benchmarkaisbench
起点 st，POST 前 tp[0]，POST 前
TTFT 首个 choices 的 timestamp − st tp[1] − tp[0]
ITL 相邻 choices 的 timestamp 差；1,023 个 diff(tp[1:])；1,024 个
usage 只读 completion_tokens，不更新时间戳 在 JSON 解析前计时，产生最后一个 ITL
latency 最后一个 choices − st tp[-1] − tp[0]
TPOT (latency − ttft) / (output_tokens − 1)；本次等于 mean ITL 同一公式；mean ITL = TPOT × 1,023 / 1,024

02 · 源码

时间点到底在代码的哪一行

两边都使用 stream_options.include_usage=true，所以流末尾都有 usage 块； 差别是时间点打在哪里，以及 usage 是否被计时。

vLLM benchmark

endpoint_request_func.py · /v1/completions 分支

choices 
if choices := data.get("choices"):
    text = choices[0].get("text")
    timestamp = time.perf_counter()

    if not first_chunk_received:
        first_chunk_received = True
        ttft = time.perf_counter() - st
        output.ttft = ttft
    else:
        output.itl.append(
            timestamp - most_recent_timestamp
        )

    most_recent_timestamp = timestamp
    generated_text += text or ""

elif usage := data.get("usage"):
    output.output_tokens = usage.get(
        "completion_tokens"
    )
    if (pt := usage.get("prompt_tokens")) is not None:
        output.prompt_len = pt

关键： usage 块的 choices 是空数组，不会进 choices 分支； 它只读 token 数，不更新时间戳；most_recent_timestamp 停在最后一个 choices。

05 · 追加实测

把 stream_interval 调到 4，ITL 变成“每 4 个 token 一次”

在容器 896bdcdfebe8 里启动 Qwen3-8B（NPU 6/7，TP=2，端口 8016）， 服务端加 --stream-interval 4；32 条 GSM8K、8 并发、每条 1024 token、 ignore_eos=true。vLLM benchmark 走代理 8006，aisbench 走代理 8007， 两次是独立运行，SSE 全部逐行落盘。

表中数字由代理 tr 复算；max 在同一份捕获内两种规则相同，说明尖峰仍发生在 choices 之间。 两条捕获的 max 不同（332.980ms vs 365.877ms）是两次独立负载的波形差异，不是规则差异。

一个 chunk 到底装了几个 token

用 Qwen3-8B 的 tokenizer 逐块复核 vLLM req_id=4： 257 块拼起来正好是 1,024 个 token。首块 <think> 只有 1 个 token， 中间 255 块各 4 个 token，末块 in requires one 是 3 个 token。

chunk 0 · <think> · 1 token → chunk 1 · 4 tokens → chunk 2 · 4 tokens ··· chunk 255 · 4 tokens → chunk 256 · 3 tokens
1 + 255 × 4 + 3 = 1,024 tokens
choices = 257；vLLM ITL = 257 − 1 = 256

ITL 的尺度跟着 chunk 走

vLLM 官方结果：mean TPOT 18.92ms，mean ITL 75.60ms； 75.60 / 18.92 = 3.996，正好是 1,023 / 256。

aisbench 官方结果：TPOT 18.4ms，ITL 73.4ms； 比值 3.981，正好是 1,023 / 257。

两个工具都没有算错，变的是 ITL 的单位：一次差分跨过约 4 个 token。 TPOT 仍然按每个 token 计算，所以它没有跟着放大。

规则差异没有变，只是被放大

  • 每条仍然只差 1 个 ITL。interval=1 时是 1,023 vs 1,024；interval=4 时是 256 vs 257。
  • usage 尾间隔仍然很小。vLLM 捕获均值 0.320ms、最大 0.668ms；aisbench 捕获均值 0.483ms、最大 4.431ms。
  • 它只稀释均值，不制造 max。两种规则在同一捕获内的 max 完全相同；均值差约 0.29ms，来自“多一个亚毫秒样本”。
  • 4 倍放大来自 chunk。不是 usage，也不是两个工具的公式突然不同。

读 ITL 时必须同时问单位

  • interval=1：1 个 ITL ≈ 1 个 token，mean ITL ≈ TPOT。
  • interval=4：1 个 ITL ≈ 4 个 token，mean ITL ≈ 4 × TPOT。
  • 跨配置比较：应看 TPOT，或把 ITL 除以每个 chunk 的 token 数；只比 ITL 会把 stream_interval 当成性能变化。
  • 跨工具比较：同一捕获内 choices 与 data 只差最后一个 usage 间隔；不要拿两次独立运行的绝对值判断公式差异。

代理复算与官方结果对照：vLLM 代理 mean 75.591ms / p99 146.910ms，官方 mean 75.60ms / p99 147.00ms； aisbench 代理 mean 73.393ms / max 365.877ms，官方 ITL 73.4ms / max 368.4ms。 代理 tr 与客户端时间点相差约一个 JSON 解析和行转发的距离，不影响口径结论。 vLLM 本次未加 --save-result，官方指标取自 benchmark 终端日志。

06 · 边界

四个容易误读的点

1. 主实验是 stream_interval=1

第 01–04 节的 1,023 vs 1,024 来自 stream_interval=1： 每条请求 1,024 个 choices，一个 step 一个 token。 第 05 节把服务端改成 --stream-interval 4 后，每条请求只剩 257 个 choices， “ITL”就变成 inter-chunk latency，不再是逐 token 间隔。

2. ignore_eos=true

主实验 64 条、追加实验 32 条都跑满 1,024 token，最后一条 choices 的 finish_reason 是 length，不是 EOS。 因此每条请求的 ITL 数量固定，方便比较。

3. 代理时间 ≠ 官方时间

代理的 tr 是行到达代理的时间；vLLM 官方时间点在 JSON 解析之后。主实验的官方 JSON 中 mean 是 41.467ms、max 是 3,033.997ms； 代理复算为 41.465ms / 3,033.897ms。差异约 0.1ms，不影响口径结论。

4. 每次捕获内部才可比

主实验的 vLLM 捕获和 aisbench 捕获不是同一次负载；追加实验也是两次独立运行。 不要把 3,033.897ms 和 347.584ms，或 332.980ms 和 365.877ms， 当成“规则导致的差异”；规则差异只在同一份捕获内比较，max 都是相同的。

一句话

ITL 是块间隔，不是天然的 token 间隔

vLLM 的 ITL 是“相邻非空 choices 块的到达差”，usage 只看 token 数； aisbench 的 ITL 是“相邻非空 data 行的到达差”，usage 也计时。 interval=1 时，本次 1,024 token 的请求得到 1,023 vs 1,024 个 ITL， 多出的 usage 尾间隔只有亚毫秒；interval=4 时，257 个 choices 得到 256 vs 257 个 ITL， 两种 ITL 都放大约 4 倍，而 TPOT 保持逐 token 的 18–19ms。
